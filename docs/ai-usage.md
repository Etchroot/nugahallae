1차 프로젝트 1~2일차(2026-10-28~29) 동안 Claude Code로 "누가할래"를 기획부터 배포·앱인토스 출시까지 진행한 기록입니다. 아래 "한눈에 보기" 숫자는 2026-10-29 기준이고, 사례 표(3~4장)는 대부분 1일차 작업입니다.
평가 항목 **AI 활용 과정**(프롬프트 변경 기록 · CLAUDE.md·스킬 활용 · AI 실수를 잡아 고친 사례)에 맞춰 정리했습니다.

## 1. 작업 방식: 사람은 결정, AI는 실행·검증

```
사용자(결정·피드백) ─▶ 메인 Claude(설계·지시서·판정·브라우저 확인)
                         ├─▶ 구현 에이전트(지시서대로 TDD 구현, 커밋)
                         └─▶ 리뷰 에이전트(diff만 보고 스펙·품질 검토)
```

- **메인 Claude**는 사용자와 대화하며 요구를 정리하고, 구현 지시서(brief)를 쓰고, 에이전트 결과를 판정하고, 마지막에 **직접 브라우저에서 플레이**해 확인했습니다.
- **구현 에이전트**는 지시서만 보고 테스트를 먼저 쓰고(RED) 구현해 통과시키는(GREEN) 방식으로 작업했습니다.
- **리뷰 에이전트**는 구현 보고서를 믿지 않고 코드 diff만 보고 검토했습니다. 구현자와 리뷰어를 분리해 "자기 코드를 자기가 검사하는" 문제를 피했습니다.

## 3. AI 실수를 잡아 고친 사례

### A. 사람(메인 Claude)이 브라우저에서 직접 잡은 것 — 테스트는 모두 통과하던 상태

| # | 상황 | 원인 | 고친 방법 |
|---|---|---|---|
| A1 | GitHub Pages에 배포했는데 **빈 화면** | 토스 디자인 시스템(TDS)이 앱인토스 밖에서는 실행을 막음. 로컬 개발 서버에선 정상이라 몰랐음 | 검사를 우회하지 않고, 데모 웹 빌드에서만 TDS 부품 7개를 자체 부품으로 바꿔 끼움(`--mode web`) |
| A2 | 폰이 **다크 모드**면 준비 화면 글씨가 거의 안 보임 | 배경색을 지정하지 않아 브라우저 기본(검정)을 따라감 | 앱을 라이트 전용으로 고정 |
| A3 | 인원수 숫자 "4"가 **회색 이모지 글꼴**로 보임 | 이모지 글꼴(Tossface)을 폰트 맨 앞에 둬서 숫자까지 바꿔 버림 | 글꼴 순서를 바꿔 이모지에만 적용 |
| A4 | 블록 탑의 **블록이 아예 안 보임**(높이 0) | 웹 대체 부품의 클래스 이름(`tw-row`)이 블록 탑 클래스와 충돌 | 접두사 변경 + **같은 클래스가 두 파일에 정의되면 실패하는 테스트** 추가(재발 방지) |
| A5 | 잔 채우기·사다리를 골라도 준비 화면에 **돌림판 규칙**이 보임 | 첫 게임만 있을 때 넣은 문구가 남아 있음 | 각 게임의 규칙만 보이게 수정 |

### B. 리뷰 에이전트가 잡은 것

| # | 버그 | 왜 위험했나 |
|---|---|---|
| B1 | 돌림판 "통과!" 연출 중에 다시 돌리기가 눌림 | 회전 도중 바퀴가 튀고 결과가 꼬임 |
| B2 | 말 뽑기에서 빠르게 두 번 탭하면 다음 사람 말이 보임 | "폰 하나로 돌려 하는" 핵심 규칙이 깨짐 |
| B3 | 게임 중 뒤로가기 창이 떠 있는데 결과 화면이 뒤에서 진행 | 가장 중요한 순간이 엉망이 됨 |
| B4 | 말 모양이 **둥근 칩** | 카지노 칩처럼 보여 앱인토스 사행성 심사 리스크 |
| B5 | 잔 채우기 도중 앱이 잠깐 백그라운드로 가면 물이 한꺼번에 쏟아짐 | 억울한 벌칙(공정성) |
| B6 | 동점자 정산 함수가 같은 값의 행을 지워 버림 | 기록 게임 순위 오류 |
| B7 | 타이머 게임에서 빠른 두 번 탭이 결과를 건너뛰고 다음 사람 타이머를 시작 | 기록이 엉뚱하게 저장됨 |
| B8 | 폭탄 돌리기 시간이 백그라운드에서 늘어남, 연타 대결이 0회로 기록됨 | 공정성 |

### C. AI(리뷰어·메인 Claude) 자신의 실수를 잡은 것

| # | 실수 | 어떻게 잡았나 |
|---|---|---|
| C1 | 리뷰 에이전트가 "통합 테스트가 통과할 수 없다(Critical)"고 보고 | 메인 Claude가 **직접 테스트를 실행**해 통과 확인 → 회전 시간 계산 착오로 판정하고 수정 지시에서 제외 |
| C2 | 메인 Claude가 `sed`로 package.json을 고치다 JSON을 깨뜨림 | 직후 JSON 파싱 검사로 발견, 커밋 전 원상 복구 |
| C3 | 잔 채우기 시제품에서 함수 이름 `top`이 브라우저 전역(`window.top`)과 충돌해 화면이 안 움직임 | 브라우저 콘솔 오류로 발견, 이름 변경 |
| C4 | 시제품의 "붓는 동안 계속 진동"이 앱인토스 정책(SDK 반복 호출 금지) 위반 | 본 구현 지시서에서 "넘치기 시작 1회 + 넘칠 때 1회"로 바꿈 |
| C5 | 구현 에이전트가 테스트를 "버튼이 이미 비활성이라 그냥 통과"하게 작성 | 리뷰어가 지적 → 실제로 실패할 수 있는 테스트로 재작성 |
| C6 | 처음 기획 "간단 내기 / 밥값 당첨"이 앱인토스 **사행성 출시 불가** 규정에 걸림 | 기획 첫 단계에서 문서 MCP로 정책 확인 → "누가할래 / 벌칙·당번"으로 전환, 금지어 자동 검사 테스트 추가 |

## 4. 프롬프트(요구) 변경 기록

사용자의 한마디가 설계를 어떻게 바꿨는지, 그리고 메인 Claude가 에이전트 지시서를 어떻게 바꿨는지 순서대로 적었습니다.

| 시점 | 사용자 프롬프트(요지) | 바뀐 것 |
|---|---|---|
| 기획 | "간단 내기(가제)가 과제·앱인토스 규정에 맞는지 판단해 줘" | 사행성 규정 발견 → 콘셉트를 **벌칙·당번 정하기**로, 이름을 **누가할래**로 |
| 기획 | "결과에 다같이 환호하는 순간", "싱겁거나 버그·복잡하면 실패" | 성공·실패 기준 → 연출, 안정성 테스트, 단순한 흐름 |
| 기획 | "생일 같은 입력 말고 색 다른 말을 각자 탭해서 뽑자" | 이름 입력 제거, **말(색+동물) 뽑기** 도입 |
| 기획 | "돌림판은 탈락식, 규칙을 화면에 분명히" | 탈락식 돌림판 + 규칙 띠 상시 표시 |
| 배포 | "영상이 아니고 실제 시연 링크를 따로 만들자" | TDS를 바꿔 끼운 **데모 웹 빌드** + GitHub Pages |
| 게임 | "소주잔 물 붓기 밈을 터치 시간으로" | 잔 채우기 시제품 → 본 게임(물컵으로 변경) |
| 디자인 | CapCut 스크린샷 + "히어로, 2열 카드, 검색, 벌칙 칸 필요 없음, 게임 100개 목표" | 홈 전면 개편, 인원수는 게임 안으로 이동 |
| 게임 | "1일차 게임 옮기기" | 8종 이식(젠가는 상표라 **블록 탑**으로) |
| 흐름 | "두구두구로 시간 끌지 말고 바로" | 결과 대기 제거, 게임 끝 연출 0.5초 |
| 흐름 | "하나씩 눌러 뽑지 말고 한 번에 보여 주고 각자 고르게" | **동물 고르기**: 한 번에 보여 주고 고른 순서 = 차례 |

### 지시서(brief)를 고쳐 간 예

- **처음**: 작업마다 지시 프롬프트에 규칙을 그때그때 적어 넣음 → 프롬프트가 길어지고, 작업마다 빠지는 규칙이 생길 위험
- **바꾼 뒤**: 공통 규칙을 파일 두 개로 분리 — `global-constraints`(금지어 목록, 햅틱 1회 원칙, 15px·44px·safe area) + `implementer-common`(TDD·커밋·보고 형식). 지시서에는 **정확한 문구·함수 이름·테스트 목록**만 적고, 구현자와 리뷰어가 같은 파일을 읽게 해 판정 기준을 맞춤
- **리뷰에서 배운 것을 지시서에 반영**: 돌림판 리뷰에서 나온 "연출 중 연타" 문제 이후 모든 게임 지시서에 탭 가드·언마운트 정리를 필수 항목으로 넣음. 잔 채우기에서 진동 정책을 정한 뒤 이후 게임 지시서에 "반복 입력마다 햅틱 금지"를 고정
- 게임 이식 때는 **공통 규칙(common.md) + 묶음별 지시서** 구조로 바꿔 8개 게임을 2번의 지시로 처리

## 5. 회고

- **잘된 점**: 구현과 리뷰를 분리하고, 마지막에 사람이 직접 플레이하는 3중 확인으로 테스트를 통과한 뒤에도 남아 있던 버그(A1~A5)를 배포 전에 잡았다.
- **아쉬운 점**: 브라우저 확인(A 유형)은 대부분 "배포·화면 확인 후" 발견됐다. 다크 모드·글꼴·CSS 충돌은 처음부터 자동 검사(스크린샷 비교 등)를 두면 더 일찍 잡을 수 있다.
- **AI를 믿지 않은 지점**: 리뷰어의 Critical 판정도 직접 실행해 확인했다(C1). AI 보고는 "주장"으로 취급하고 증거(테스트 출력, 브라우저 화면)로 판정했다.
